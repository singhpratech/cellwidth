01 / The instrument

Measure anything, right now

This is not a simulation. The panel below is the actual crate, compiled to WebAssembly and running in your browser. Same code, same Unicode tables, same answers as your terminal build.

cellwidth.wasm loading…

Each box is one grapheme cluster, drawn across the terminal cells it occupies. Violet = 2 cells, grey = 1 cell, red = zero-width (a combining mark or an escape sequence — it costs nothing).

Truncate without breaking anything

truncate(s, n) & cell(s, n)

truncate borrows the longest prefix that fits — never splitting a character or leaving half an escape sequence. cell guarantees exactly n columns, adding an ellipsis or padding. The amber frame is the target width; hatching is padding. Every glyph sits in a real cell, so nothing here depends on your browser’s font metrics.

Wrap at real break opportunities

wrap(s, n) — UAX #14

Japanese has no spaces, so naive whitespace wrapping produces one giant line. wrap implements the Unicode line-breaking algorithm and breaks between characters where the script allows it.

02 / The problem

Three different numbers, and only one is the right one

A terminal is a grid of fixed-size cells. To draw anything that lines up — a table, a border, a progress bar, a status line — you must know how many cells a string occupies. Rust gives you two numbers, and neither is that one.

String.len().chars()Terminal cellsWhy
café554the accent is a combining mark, drawn on top
日本語936East Asian wide — two cells each
👨‍👩‍👧‍👦2572four people joined by ZWJ into one glyph
🇯🇵822two regional indicators form one flag
\e[31mred\e[0m14143colour codes are instructions, not ink

Reach for len() and your output goes ragged the first time someone has an umlaut in their name, a Japanese hostname, or an emoji in a commit message. It stays broken, because the failure only shows up on other people's data — never yours.

03 / Why this exists

Four crates, and the bug lives in the glue

You can already solve parts of this. The problem is that the parts don't fit together, and joining them is where people get it wrong.

Before

unicode-width        // widths
unicode-segmentation // clusters
strip-ansi-escapes   // colour
textwrap             // wrapping
+ glue you write yourself

Width and segmentation are different questions, and those two crates do not talk to each other. Nothing stops you from measuring a string one way and cutting it another — which is exactly the bug.

After

cargo add cellwidth

// cargo tree
your-app v0.1.0
└── cellwidth v1.0.0

One crate. Zero dependencies, zero dev-dependencies, no build script. Every operation works in whole grapheme clusters and whole escape sequences, so a cut can never produce half a character or half a colour code.

It also runs where the others can't. no_std with optional alloc, verified on a bare-metal thumbv7em-none-eabi build — so width, truncate, graphemes and pieces work in a serial console or an embedded shell with no allocator at all.

Eight real defects were found this way — none of them by re-reading the code. Each has a regression test naming the oracle that caught it. That is the entire argument for testing against something external: the bugs you can find by staring are not the bugs that are there.

Coverage, stated exactly

That last row is the honest one. A single region is reported missing, but the report's own segment data contains no uncovered segment for that file, and a library-only run shows the lines covered. It is an artifact of how per-binary reports are merged, not a hole in the suite — so it is reported and explained rather than rounded away or quietly hidden.

Terminals genuinely disagree — so we measured instead of guessing

There is no single right answer for how wide an emoji is. Rather than pick one and hope, probe/ prints a string into a live terminal, asks where the cursor ended up with CSI 6n, and writes the answer down.

Two camps, so there are two presets. Width::DEFAULT reproduces kitty exactly on all 32 cases. Width::LEGACY counts every code point separately, as wcwidth does, and scores higher across the four as a group (99/128 vs 94/128). Flip between them in the demo above and watch the numbers move.

06 / Using it

The whole API, roughly

use cellwidth::{width, cell, truncate, wrap, Table};

assert_eq!(width("café"), 4);                // combining accents are free
assert_eq!(width("日本語"), 6);               // CJK is double-width
assert_eq!(width("👨‍👩‍👧‍👦"), 2);                  // one glyph, not seven
assert_eq!(width("\x1b[31mred\x1b[0m"), 3);  // colour costs nothing

// exactly 10 columns, always — truncated with an ellipsis or padded
assert_eq!(width(&cell("🇯🇵 Tōkyō 東京", 10)), 10);

Tables that line up

let out = Table::new()
    .column("host")
    .column_with("label", Align::Left, Sizing::Max(22))
    .column_aligned("rps", Align::Right)
    .row(["tokyo-cdn", "🇯🇵 Tōkyō 東京 edge", "17,900"])
    .row(["crew-alpha", "👨‍👩‍👧‍👦 shared account", "3"])
    .border(Border::Ascii)
    .render(Some(60));

A flag, a ZWJ family, CJK and a macron in one column — and all six lines measure 44 cells exactly. That invariant is what the fuzzer asserts, whatever the cells hold.

Where this shows up

Anything that draws a fixed grid into a terminal: CLI tables and reports, TUI list and column views, progress bars and spinners, log formatters, box-drawn banners, help and error text wrapped to $COLUMNS, and text inputs where the cursor should move by characters rather than bytes.

Coming from unicode-width or unicode-segmentation

Same trait names, same method signatures, cellwidth's answers. The figures are measured by the oracle tests, not quoted.

// use unicode_width::UnicodeWidthStr;
use cellwidth::compat::{UnicodeSegmentation, UnicodeWidthStr};

assert_eq!("\x1b[31mred\x1b[0m".width(), 3);  // unicode-width 0.2.2: 12
assert_eq!("क्षि".width(), 1);                // unicode-width 0.2.2: 3
assert_eq!("a👍🏽🇯🇵".graphemes(true).count(), 3);

Head to head

Best of seven rounds of 100,000 calls. Read the answers before the timings: unicode-width neither segments clusters nor parses escapes, so on those inputs it does less work and returns a number the terminal will not honour. Width::LEGACY is the like-for-like model.

inputcellwidth::widthWidth::LEGACYunicode-widthanswers
ascii, 69 B49 ns46 ns54 ns69 / 69 / 69

Grapheme iteration runs about twice as fast as unicode-segmentation on every input (233 ns vs 519 ns for the CJK string).
